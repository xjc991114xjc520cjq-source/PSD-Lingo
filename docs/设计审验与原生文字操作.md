# 设计审验、修改指导与原生文字操作

本次在 0.3.61 源码上补齐；本地开发版，未发布到更新渠道。

## 在软件内使用

1. 在 AI 助手选择本机 Codex 和模型，导入原稿与批准文案，先选择输出文件夹。助手沿用已保存的 Codex 项目设置。
2. 描述要保留的视觉方向和需修复的问题。软件先核对已有目标语、转曲文字及文案覆盖，再使用对应文字编辑能力，避免新增重复消息。
3. 设计规划先看整页，一次处理相关标题、副标题、说明和参数组件。第三方设计方法按当前画面的职责选择适用部分；不同技能意见合并为修改清单。
4. 清单包含结构根因、真实对象引用、联动修改、依赖顺序和视觉验收标准。已绑定可编辑文字的清单会随下一次设计规划自动传入；隐藏、清除、补字由助手通过对应软件工具完成，清单本身不授权任意图案编辑。
5. 候选实际渲染后复审，最终整页审核后另存原生副本。审验未通过会保留待修状态及原因，不能称作制作完成。明确缺陷直接进入修改；只有看不清时补同状态细节图。

## 实际可执行的对象能力

- `create_text`：引用已导入的批准文案，在已验证的画板中建立可编辑文字，指定已安装字体、字号、颜色和对齐；支持 AI、PSD、PSB。
- `set_text_presence`：隐藏、清除或恢复可编辑源文字；清除在导出副本中真正移除原生对象，恢复保留此前绑定及布局。
- `inspect_artwork` + `set_artwork_visibility`：先看原稿局部与隐藏候选后的真实对照，再隐藏或清除经核对的 AI 文字／纯矢量小组。全转曲画板可由已验证候选确定画板后新增可编辑译文。
- 以上修改支持 Ctrl+Z、重做、保存项目和重新载入；语言模板保留新增文字及对象处理。未知图案、任意位图擦除、复杂转曲改写不在这些工具范围内。
- 原稿不变，写入都发生在副本。新增、移除及可见性改变会让旧预览与审验缓存失效。

## 设计方法与真实运行方式

内置跨品牌构图方法之外，随软件携带两个有固定版本和许可的来源：

- [Anthropic Design 1.2.0](https://github.com/anthropics/knowledge-work-plugins/tree/e605d8ddbfb688da57dfaaceebd93f12a64ef1d3/design)：design-critique、design-system、accessibility-review，Apache-2.0。
- [Amir Design Judgment](https://github.com/amirmushichge/amir-design-judgment/tree/bb0852f5f28742886fcaf4638a302258a438d5d0)：graphic-judgment，CC-BY-4.0，作者 Amir Mušić。

固定提交、技能内容 SHA256、原许可和原插件元数据都在 `services/design-plugins`。这些上游插件不在软件中伪装成 Codex 原生插件：采用用户要求的图像回交方式，把真实当前图和技能原文交给同一本机 Codex 会话执行。没有 API 降级，也没有另请一个模型。基础设计批评和图形判断必须执行；系统一致性、可访问性按画面报告适用范围，同页可同时使用多份方法。静态海报不套键盘／触控要求，不声称测得压缩图片的精确对比度。

每份适用技能都要留下可见关系及判断依据，缺项、跳过基础方法、未通过项没有修改指导、指导引用未知对象或依赖循环，软件都会拒绝。技术可读、没有碰撞、保存成功不能代替设计通过。实际图像和最终用户审美仍是检验依据，不承诺任意作品一次绝对完美。

## 避免重复消耗

- 首次规划集中诊断整页并联合提案，相关对象作为关系组一起验证、一起应用或保留。
- 多技能意见合并为同一份清单，不拆成多个模型任务。清单附带下一轮，禁止逐项遗忘后重改。
- 相同被否决提案不再渲染和复审；相同要求、画面、模型、规则与参考下的无进展结果不可用 replan 强行循环。
- 明确失败不再为碰运气重复整页审验。仅不确定项补细节图；同状态结果缓存复用，用户补充、文案、模型、规则、参考、对象或当前画面变化时失效。
- 修正后仍保留一次实际图核验，不能省掉验证而直接承诺“完美”。

## 学习库

`services/localization-knowledge.json` revision 8 是不到十余 KB 的跨作品规则数据，增加联合诊断、依赖修改及停止无进展规则；没有客户 AI/PSD、截图、文案正文、样本金额、绝对坐标。每次任务重读最新受校验文件。已有后台同步仍负责跨电脑交换小文件，规则更新不等于自动执行未经授权的图案修改，也不替代程序能力升级。

## 开发验收入口

普通自动检查：`node --test tests/*.test.cjs`。

Adobe 验收必须在用户确认空闲后，显式给测试进程设置 `SPARKIT_NATIVE_FIXTURE=1`、`TEMP=TMP=D:/PSD-Lingo/work/temp`。按顺序运行 Electron：

1. `tests/native-text-objects.adobe.electron.cjs` 创建独立 AI/PSD 夹具，验证隐藏、清除、新增、保存重开和源哈希。
2. `tests/native-text-formats.electron.cjs` 使用上述独立夹具，检查 AI 多行居中/右对齐与 PSB 可编辑新增文字。
3. `tests/native-text-objects.electron.cjs` 使用真实 renderer/preload，检查工具、撤销重做、项目存取、隐藏和清除状态。
4. `tests/design-repair-live.electron.cjs` 另建独立 AI 测试稿，调用真实本机 Codex（gpt-6.1-sol），完成规划、候选复审、整页审验、原生保存重开；会实际使用当前本机 Codex 连接。可用 `SPARKIT_NATIVE_OUTPUT` 指定新的证据目录，避免覆盖上次日志。

这些显式测试不会扫描客户目录或读取客户稿件。实际客户成稿需另按任务验收，独立测试不能冒充 RS6V2 成稿批准。
# AI 最终交付图审验补充

AI 助手的 export_files 会先保存并重开新 AI，再导出已修改目标画板的 JPG。软件检查产物数量、尺寸、可解码性和文件哈希后，把实际 JPG 及必要局部交回同一本机 Codex，执行六项检查、四项设计审验和适用设计技能审验。工作区预览不再作为 AI 最终交付通过的依据。

结果分别报告原生保存、重开、JPG 核验、最终审验。任何阶段失败均保留已保存副本及原因，不能称为制作完成；模型通过仍需用户确认成稿。相同计划可复用 AI/JPG，但原稿或任一产物变化后不可沿用旧审验。
